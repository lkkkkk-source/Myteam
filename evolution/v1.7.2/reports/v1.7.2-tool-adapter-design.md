# MyTeam v1.7.2 Tool Adapter Design

> 阶段：v1.7.2 — **Tool Adapter 设计**（Runner 的 ToolInvocationPort → 真实 OpenCode Tool 的适配层契约）。
> 前置：v1.6.0 Plugin Entry / v1.6.3 Tool Bridge Context / v1.6.5 Execution Persistence / v1.6.7 Execution Engine / v1.7.1 Runner Core。
> 约束：**只设计，不写代码**；不直接修改 OpenCode 配置；不绕过 Tool Bridge。

---

## 1. Current OpenCode Tool Model

### 1.1 Plugin Entry（`plugin/opencode/index.ts`）

OpenCode 单一入口插件。当前可观察到的工具暴露面：

| 工具 | 类型 | 能力 |
|---|---|---|
| `myteam` | 自定义 tool | 入口：把请求转发给既有 PM agent（不选 Agent、不执行） |
| `myteam.status` | 自定义 tool | 只读：MyTeam 平台状态（agents/registry/deployment） |
| `myteam.execution.admit` | 自定义 tool | 只读：检查已批准的 Execution + 权限 |
| `myteam.execution.refuse` | 自定义 tool | 只读：拒绝 Action 生成 |
| `myteam.execution.cancel` | 自定义 tool | 取消 Execution |

宿主事件钩子（v1.6.0）：

- `tool.execute.before`：在宿主 write/edit 前做 `guardHostWrite` 拦截（拒绝写 `~/.config/opencode` 域）。
- `event`（`server.connected`）：日志确认隔离状态。

**结论**：当前 plugin 只暴露**只读聚合 + 治理钩子**；**没有任何"实际调用宿主原生工具（read/grep/glob/edit/write/bash）"的通道**——v1.6.x 全程保持隔离，宿主工具由宿主自身直接驱动，不经过 MyTeam。

### 1.2 Bridge Layer（`bridge.ts`）

`bridge(resolution, teamStatus)` 产出 `MyTeamRuntimeView`（registry/agents/deployment + 隔离信息），纯只读聚合。
`guardHostWrite(targetPath)` 是唯一的写侧安全门禁（拦截 `.config/opencode/opencode.json` 域）。
两者都不执行宿主工具。

### 1.3 MCP 入口（`config.mcp` + `mcp-resolver.ts`）

- `config.mcp`：MyTeam 平台的 MCP 注册（如 `context7`，`command: npx -y @upstash/context7-mcp`）。
- `mcp-resolver.ts`：把 AgentDefinition.mcp[] 解析为 `McpCapability[]`（绑定到 Agent 声明的能力，引用 registry，不写宿主配置）。
- Tool Bridge `context.mcp`：`AgentExecutionContext.mcp` 携带该 agent 的 MCP 能力（provides[]/source）。

**现状**：MCP 在 MyTeam 侧只是**静态能力绑定**（声明 + 解析），**调用通道尚未建立**——v1.6.x 所有层都不触发真实 MCP 调用，宿主 MCP（OpenCode 的 mcp server）由宿主驱动，不经过 MyTeam。

## 2. Tool Adapter Boundary

### 2.1 调用链路（设计目标态）

```
Runner (v1.7.1)
   │  ToolInvocationRequest（已校验：allowed=true / 路径在安全域内）
   ▼
ToolInvocationPort（v1.7.1 定义，当前 mock）
   │
   ▼
Tool Adapter（v1.7.2）  ← 本次设计
   │  二次校验（§3）+ OpenCode 工具/MCP 映射（§4）+ 错误归一（§5）+ 安全门禁（§6）
   ▼
OpenCode Tool（宿主原生工具 / 宿主 MCP server）
```

### 2.2 边界原则

1. **单向**：Adapter 是 Runner 下行工具能力的**唯一通道**；Runner 不绕过 Tool Bridge 直连宿主工具。
2. **二次校验**：Adapter 是 Tool Bridge 的「执行侧」——它不是重新做能力绑定（那是 Tool Bridge 的事），而是**消费 Tool Bridge 产出的安全域 + 权限**，在真正下发前**再次确认**（纵深防御）。
3. **不绕过 Tool Bridge**：Adapter 不修改 AgentExecutionContext，不修改 security，不写 opencode.json；它只**读取** Runner 校验后转发下来的请求做二次确认。
4. **不直接写宿主**：Adapter 自身不写 `~/.config/opencode`；写宿主工具由 OpenCode 宿主执行，Adapter 只做拦截判断（§6）。

### 2.3 Request / Response 契约

#### ToolAdapterRequest（下行请求）

```
ToolAdapterRequest
  ├─ tool          : string               // = ToolInvocationRequest.tool
  ├─ source        : "host" | "mcp"
  ├─ arguments     : Record<string, unknown>
  ├─ allowed       : boolean             // Runner 校验后的 allowed（必须 true 才下发）
  ├─ security      : SecurityContext     // 来自 AgentExecutionContext.security
  ├─ agent_ctx_ref : {
  │     execution_id : string
  │     instance_id  : string
  │     agent        : string
  │   }
  └─ signal?       : AbortSignal         // 宿主取消
```

#### ToolAdapterResponse（上行响应，对应 Runner 的 ToolInvocationResult）

```
ToolAdapterResponse
  ├─ ok            : boolean
  ├─ value         : unknown             // 宿主工具真实返回值
  ├─ error?        : string             // ok=false 时
  ├─ error_kind?   : RunnerErrorKind     // 归一后的错误分类（§5）
  ├─ duration      : number
  └─ trace_hint    : string             // 仅用于诊断的链路标注（不是 Trace 事件）
```

> **Runner ↔ Adapter 接口一致**：`ToolInvocationPort.invoke(req) → ToolInvocationResult` 的形状不变；
> 只是把 v1.7.1 的 mock 实现替换为真实的 `ToolAdapter.invoke()`。Runner 侧无需改动。

## 3. Permission Enforcement（二次验证）

Adapter 在下发前**必须**做二次验证（即使 Runner 已校验过——纵深防御，防止 mock 被替换 / 校验逻辑漂移）：

| 校验项 | 数据源 | 失败动作 |
|---|---|---|
| **agent permission** | `ctx.permissions.read/edit/execute` | `error_kind = assertion_error`，不下发 |
| **tool capability** | `ctx.tools[]`（tool 是否声明 + allowed） | `error_kind = assertion_error`（与 Runner 校验一致） |
| **security domain** | `ctx.security.allowed_paths/deny_paths` | 路径类参数越域 → `error_kind = assertion_error` + 不转发 |
| **MCP 绑定** | `ctx.mcp[]`（source=mcp 时） | MCP 未绑定 → `error_kind = tool_error` |

**执行规则：**

- host 工具：`read` 工具需 `permissions.read=true`；`edit/write` 需 `permissions.edit=true`；`bash/execute` 需 `permissions.execute=true`。
- 副作用类工具（write/edit/bash）还要求**路径 ∈ allowed_paths 且 ∉ deny_paths**。
- 校验全部通过后，才把请求下发给宿主；任一失败 → 返回 `ok=false` + 对应 `error_kind`，**不发起宿主调用**。

## 4. MCP Mapping

`AgentExecutionContext.mcp`（`McpCapability[]`）到实际调用的映射规则：

| 映射项 | 设计 |
|---|---|
| **MCP 名称** | `ctx.mcp[].mcp` = 宿主 MCP server 名（如 `context7`） |
| **工具全名** | `mcp:<mcp>`（宿主命名空间）；调用时拆为 `{ server: mcp, method: <tool> }` |
| **能力引用** | `ctx.mcp[].provides[]` 是该 MCP 提供的能力标签；Adapter 只读，不解析能力语义 |
| **注册源** | `ctx.mcp[].source` = `McpRegistry` 项（来自 `config.mcp` + mcp-resolver）；Adapter 引用 registry 决定"是否已绑定" |
| **执行体** | 宿主 OpenCode 的 MCP client（非 MyTeam 自建）；Adapter 只做"引用"，不启动 MCP server 进程 |

**规则：**

- `source=mcp` 的请求：Adapter 校验 `ctx.mcp` 中存在匹配项 → 映射为宿主 MCP 调用 `{ server, tool, args }`。
- 未绑定（mcp-resolver 标记 unsupported）→ `error_kind = tool_error`，不下发。
- **Adapter 不启动 / 不管理 MCP 进程**；MCP server 生命周期归宿主。

## 5. Error Mapping（OpenCode error → RunnerError）

宿主工具 / MCP 调用返回的错误归一为 Runner 的 `RunnerErrorKind`（§5 一致）：

| OpenCode / MCP 错误 | RunnerErrorKind | 说明 |
|---|---|---|
| 工具未找到（宿主无此 tool） | `tool_error` | 宿主层不可达 |
| 工具执行失败（读 IO 错误 / 写被宿主拒绝） | `tool_error` | 可重试（Runner 重试策略） |
| 宿主拒绝写（`guardHostWrite` 拦截命中） | `assertion_error` | 安全域拦截（不可重试） |
| 路径越出安全域（§3 二次校验命中） | `assertion_error` | 不发起宿主调用 |
| 工具参数校验失败（宿主 schema 拒绝） | `tool_error` | 不可重试（参数错，重试无效） |
| 宿主超时 | `timeout` | Runner 超时语义 |
| 取消（宿主取消 / Runner cancel） | `cancel` | Runner cancel 语义 |
| MCP server 不可达 | `tool_error` | 宿主 MCP 连接失败 |
| 宿主异常（非标准） | `agent_error` | 兜底（宿主自身崩溃） |

**Rule**：
- 副作用类（write/edit/bash）的失败 → 一律 `ok=false`，**不自动重试**（由 Runner 的 `tool_error` 策略判断；Adapter 不自行重试）。
- 安全域类失败 → 一律 `assertion_error`，不重试。
- Adapter 把错误**归一 + 标注**，重试决策留在 Runner（与 v1.7.1 分层一致）。

## 6. Security Boundary（确认禁止）

Adapter **必须**确认以下路径 / 操作被禁止（与 v1.6.0 隔离契约 + guardHostWrite 一致）：

| 禁止项 | 实现位置 | 说明 |
|---|---|---|
| **MyTeam Home** 写 | `ctx.security.allowed_paths` 不含 Home + `guardHostWrite` | Home 是平台源域，Agent 只读 |
| **`~/.config/opencode`** 写 | `guardHostWrite`（bridge.ts）+ deny_paths | 宿主 opencode.json 不可覆盖 |
| **Host 修改**（批量复制 / 污染全局） | `index.ts` 隔离契约（copiedFiles=0） | 卸载后宿主无残留 |

**确认规则：**

- Adapter 在 §3 二次校验中把上述路径加入**路径黑名单检查**（命中即 `assertion_error`，不下发）。
- 宿主工具的**写操作**最终由 OpenCode 宿主执行；Adapter 只负责"下发前拦截"——若拦截失败（宿主侧越权）由 `guardHostWrite` 兜底。
- **Adapter 自身从不写磁盘**；它只是"下行校验 + 上行归一"，所有写动作都在宿主工具层。

## 7. 模块落点（未来实现提示，v1.7.3+）

```
runtime/tool-adapter/
  ├── index.ts            // 出口
  ├── adapter.ts          // ToolAdapter：invoke() 实现（二次校验 + 宿主调用 + 归一）
  ├── permission-check.ts // §3 二次校验
  ├── mcp-map.ts          // §4 MCP 映射
  ├── error-map.ts        // §5 错误归一
  ├── security.ts         // §6 安全域 / 黑名单
  └── test/adapter.test.ts
```

分层（与 Runner 一致）：
`Runner → ToolInvocationPort → ToolAdapter → OpenCode Tool（宿主）`。
Adapter 是唯一接触宿主工具的层；Runner 不直连。
