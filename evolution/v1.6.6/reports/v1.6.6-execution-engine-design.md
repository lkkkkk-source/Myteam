# MyTeam Execution Engine — v1.6.6 Design

> 阶段：v1.6.6 — **Execution Engine（设计）**。
> 目标：把 v1.6.5 的 Execution Store（纯持久化）升级为**可管理的任务执行生命周期**——提供状态转移、暂停/恢复、Checkpoint 接入、AgentRun 生命周期与错误恢复的驱动接口。
> 范围：**只设计生命周期驱动。** 不启动 Agent、不调用 Tool、不实现 Runner、不实现 Trace、不写代码。
> 依赖：v1.6.0 Workspace Binding（`Resolution`）、v1.6.1 AgentRuntimeInstance、v1.6.3 AgentExecutionContext、v1.6.5 Execution Store（`runtime/execution/execution-store.ts`）。
> 状态枚举（沿用 v1.6.5，Engine 只驱动不新增）：
> `received → planning → awaiting_confirmation → ready → running → paused → completed / failed`

---

## 1. Engine Boundary

三层契约（不变换，Engine 只做第三步）：

```
Router   : 只选择 → 输出 ExecutionPlan（计划 / 选人 / 阶段划分）
Runtime  : 只实例化 → 输出 AgentRuntimeInstance（v1.6.1）+ AgentExecutionContext（v1.6.3）
Engine   : 只管生命周期 → 接收 plan + instances，驱动 Store 落盘 + 在合法状态间转移
```

| 层 | 输出 | 对 Store 的访问 | 禁止 |
|---|---|---|---|
| Router | `ExecutionPlan` | 只读（load/list） | 创建 Run、推进状态 |
| Runtime | `AgentRuntimeInstance` | 只读（load instance） | 推进状态 |
| **Engine** | 状态转移 / Run / Checkpoint 驱动 | **读写（save/saveRun/saveCheckpoint…）** | 启动 Agent、调用 Tool |

**Engine 的输入**：`Resolution` + `ExecutionPlan`（含 execution_id、目标 stage 序列、候选 agents）+ 已实例化的 `AgentRuntimeInstance[]`。
**Engine 的输出**：对 Store 的一次次 `save` 调用——**所有状态变化都通过 Store 落盘**，Engine 自身不持有易失状态（状态真相在 `.team/runtime/execution/`）。

**Engine 是否持有内存态**：不。每次 `transition()` 先 `store.load()` 读当前真相，再判定合法性、写回。天然满足**进程崩溃恢复**与**重复调用幂等**。

## 2. State Driver

### 2.1 接口

```ts
transition(exec: Execution, to: ExecutionStatus): Execution   // 核心：合法转移
pause(exec: Execution, reason?: string): Execution            // → paused
resume(exec: Execution): Execution                            // → running（或按 checkpoint 规则恢复）
complete(exec: Execution): Execution                          // → completed（终态）
fail(exec: Execution, reason?: string): Execution             // → failed（终态）
```

### 2.2 状态转移表（Engine 唯一合法转移来源）

| from \ to | planning | awaiting_confirmation | ready | running | paused | completed | failed |
|---|---|---|---|---|---|---|---|
| **received** | ✅ | – | – | – | – | – | ✅（失败接管） |
| **planning** | – | ✅ | ✅（无 checkpoint 时可直接 ready） | – | – | – | ✅ |
| **awaiting_confirmation** | – | – | ✅（continue/modify 后） | – | – | – | ✅（reject→可选 fail） |
| **ready** | – | – | – | ✅ | ✅（手动暂停） | – | ✅ |
| **running** | – | ✅（遇到 checkpoint） | – | – | ✅（中断/超时） | ✅ | ✅ |
| **paused** | – | – | – | ✅（resume） | – | – | ✅（放弃） |
| **completed** | – | – | – | – | – | – | – |
| **failed** | – | – | – | – | – | – | – |

终态不变量：**`completed` / `failed` 为吸收态**——任何转移到它们之后，`transition()` 一律拒绝再次变更（幂等 + 防重放）。

### 2.3 不变量

1. **单一真相**：状态以 `store.load()` 结果为准；Engine 从不盲目信任调用方传入的 `exec`。
2. **合法性校验**：所有转移经 `2.2` 表判定；非法转移抛 `EngineTransitionError`（不落盘）。
3. **快照式写回**：每个转移 = 一个 `store.save()` 原子写（复用 v1.6.5 `writeAtomic`）。
4. **幂等**：转移到目标态再调同目标 → no-op 返回当前态（不重复写）。
5. **不引入新状态**：Engine 不扩展 `ExecutionStatus` 联合。

## 3. Checkpoint Integration

### 3.1 进入 `awaiting_confirmation`

Engine 在 `running` 阶段、于 Router 计划的"人类决策点"处触发：

```
Engine.raiseCheckpoint(exec, { type, stage, message, required_action, options })
  1. store.saveCheckpoint(cp, executionId)          # 先落盘检查点（含 cp-0001 递增 id）
  2. transition(exec, "awaiting_confirmation")      # running → awaiting_confirmation
  3. 返回 Checkpoint（等待 human 响应；Engine 不阻塞，不自动通过）
```

规则：
- checkpoint 写入与状态转移**分两个原子写**（先 cp 后 status）——保证人类即使看到状态已 waiting，也必然能读到对应的 cp 文件。
- **机不自动通过**：进入 `awaiting_confirmation` 后，Engine 不再自行推进；必须有 `resolveCheckpoint()` 显式响应。

### 3.2 恢复（human 响应）

```
resolveCheckpoint(exec, cpId, resolution, { resolved? })
```

| resolution | 行为 | 目标态 |
|---|---|---|
| `continue` | 校验 cp 未响应 → 标记 acknowledged/resolved_at → 回到运行 | `ready → running` |
| `modify` | 标记 + 记录 `resolved`（修改意图）→ 回到规划 | `awaiting_confirmation → planning` |
| `reject` | 标记 + 记录 → 终止任务 | `awaiting_confirmation → failed`（终态） |

每个响应 = **一个 checkpoint 落盘（saveCheckpoint）+ 一个状态转移（save）**，两次原子写、两次幂等校验。

### 3.3 规则

- **每个 checkpoint 只响应一次**：已 `resolved_at` 的 cp 再次 resolve → no-op / 抛错（防重复）。
- **不自动确认**：Engine 提供 `resolveCheckpoint()` 入口，由人类或代理调用；Engine 不自行填 `acknowledged`。
- **独立存储**：检查点与执行状态分文件存（对齐 v1.6.5 目录 `checkpoints/`），便于审计"人类何时、如何干预"。

## 4. Agent Run 生命周期接口

只设计驱动，**不启动 Agent**：

```ts
createRun(exec, { agent_instance_id, input })   → AgentRun（status=received，id 由 Engine 递增：run-0001）
startRun(exec, runId, { started? })             → AgentRun（status=running）
completeRun(exec, runId, { output, completed? })→ AgentRun（status=completed）
failRun(exec, runId, { output, completed? })    → AgentRun（status=failed）
```

| 方法 | 写盘 | 对 Execution 的影响 |
|---|---|---|
| `createRun` | `store.saveRun(run)` | 无（仅登记；若 Execution 为 received/planning 可选顺带 transition 到 running） |
| `startRun` | `store.saveRun(run)` | 若 Execution 在 ready → 转移 `ready→running` |
| `completeRun` | `store.saveRun(run)` | 不自动改 Execution（由调度层决定是否 complete） |
| `failRun` | `store.saveRun(run)` | 不自动改 Execution（由错误恢复决定是否 fail） |

规则：
- **引用不复制**：`createRun` 只带 `agent_instance_id`（v1.6.5 测试 6 已保证 YAML 无嵌套 instance 对象）。
- **状态分离**：`AgentRun.status` 独立于 `Execution.status`（一个 Execution 可多次 createRun）。
- **run id 递增**：Engine 负责 `run-0001` 递增（v1.6.5 将命名权留给上层，Engine 就是上层）。
- **不启动 Agent**：四个方法只写 run 记录 +（可选）转移 Execution；把 Agent 交给"调用方的 Runner/调度"去真正执行。

## 5. Persistence Integration

Engine → Store 调用映射（全部经由 v1.6.5 接口，Engine **不直接操作 fs**）：

| Engine 操作 | Store 调用 |
|---|---|
| 初始化/读取当前态 | `store.load(res, executionId)` |
| 创建 execution | `store.create(res, exec)` |
| 状态转移 | `store.save(res, exec)` |
| 列项目任务 | `store.list(res)` |
| AgentRun 写入 | `store.saveRun(res, run, runId)` / `loadRun` / `listRuns` |
| Checkpoint 写入 | `store.saveCheckpoint(res, cp, executionId)` / `loadCheckpoint` / `listCheckpoints` |
| 结果产出 | `store.saveResultArtifact(res, executionId, srcAbs, name?)` / `loadResultArtifacts` |

规则：
- **Engine 是 Store 的读写者，Store 是磁盘的唯一入口**——Engine 永不直接 `fs.*`，保证路径安全与原子写在单点（Store）内一致。
- **先写后转**：所有"写子记录 + 改状态"的组合，一律先写子记录（run/cp/artifact），后转移状态；顺序保证日志永远可追。
- **幂等重试**：Engine 对每个 Store 调用的失败（IO 异常）做"重读当前态再判定"而非盲目重写。

## 6. Error Recovery

### 6.1 失败恢复（failed → 重跑）

```
场景：某次 startRun 后 Agent 抛错，Execution 停在 running 或 failed。
恢复：failRun(run) → 记录 output → transition(exec, "failed") 或（可选策略）回到 planning 重规划。
```

| 策略 | 行为 | 适用 |
|---|---|---|
| `retry` | `failRun` → 重新 `createRun`（新 run id）→ `startRun` | 瞬时故障 |
| `replan` | `fail` → `transition(planning)` → Router 重出 plan | 计划失效 |
| `abort` | `failRun` + `fail(exec)` → 终态 | 不可恢复错误 |

### 6.2 暂停恢复（paused → resume）

```
场景：running 中用户/系统暂停（中断、超时、人工打断）。
恢复：resume(exec) → transition(paused→ready→running)。
```

- **恢复点定位**：Engine 以 Store 中**最后一个未 completed 的 run** 作为恢复点；`resume` 重新 `startRun` 该 run（或新建 run 承载"续跑输入"）。
- **不丢中间产物**：paused 前已 `saveRun`/`saveResultArtifact` 的记录保留，resume 后作为上下文读取。

### 6.3 重复调用幂等（防重放）

| 输入 | 行为 |
|---|---|
| `transition(exec, completed)` 但已 completed | no-op 返回当前态（不写盘） |
| `resolveCheckpoint(cpId)` 但已 resolved_at | no-op / 抛"已响应" |
| `createRun` 同名 runId 已存在 | 抛 `EngineDuplicateRunError`（防覆盖） |
| `transition` 非法边（如 completed→running） | 抛 `EngineTransitionError`（不落盘） |
| 进程崩溃后重放完整流程 | 每次先 `store.load()` 读真相 → 状态已达成则跳过，未达成则补齐 |

**崩溃一致性**：由于状态真相全在磁盘且每次转移是单原子写，崩溃恢复 = 重新 `load` + 重放剩余合法转移，**无需日志回放**（v1.6.5 限制 6 的"单文件原子"正是为此打底）。

## 7. 交付边界（严格范围确认）

- ✅ 设计：Engine Boundary / State Driver（transition/pause/resume/complete/fail）/ Checkpoint Integration / AgentRun 生命周期接口 / Persistence Integration / Error Recovery。
- ❌ 未设计：Agent 启动、Tool 调用、Runner、Trace Event Bus、OpenCode 工具实际执行。
- ✅ 分层契约保持：Router 只选 → Runtime 只实例化 → **Engine 管生命周期** → 后续 Runner 真正执行。

1. **v1.6.6 仅设计**：本文是设计文档，未落任何 `execution-engine.ts` 代码。

3. **不新增状态**：状态集与 v1.6.5 完全一致，不引入新字段到 `Execution`。
