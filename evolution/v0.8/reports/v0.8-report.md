# Runtime Action Proposal & Approval Layer — v0.8 Report

> 阶段：v0.8 · **Runtime Action Proposal & Approval Layer**（在 v0.7 Runtime Contract 之上，为具体运行时动作建立提案/批准治理层）
> 目标：v0.7 定义了模块级协作契约（哪个模块、哪个只读消费者），但对**更具体的运行时动作**（跑命令 / 部署 / 发布 / 写文件）还缺少执行前的治理。v0.8 在 v0.7 之上，定义 **Action Policy（什么动作 / 什么风险 / 谁批准）** + **Action Proposal（单一动作提案）** + **Action Ledger（集成台账）** + **Snapshot（只读留底）**。
> 升级前基线：Agent=30 MCP=5 Skill=26 Workflow=8（**不变**）
> 状态：完成（Action Policy 设计 + Proposal 记录 + Ledger 台账 + 快照 + 一致性测试通过；未实现任何自动执行 / 调度 / 切换 / 选择 / 批准）

## 1. 分层定位（v0.8 在链路中的位置）

在既有协作链路（Router → Team → Agent → Model Recommendation → Scheduler → Execution → Quality → Observability → Evolution）之上，v0.8 为 **Execution 之前的具体动作**加入治理闸门：

```
... → Scheduler（产出计划）
        ↓
   Action Proposal（具体动作提案） ← Action Policy（风险/批准模型）
        ↓
   Action Approval（medium=PM / high=human）
        ↓
   Execution Interface（本阶段【不】实现）→ ...
```

> 本层只完成 **提案 → 批准** 的记录与治理；批准通过后**不真正执行**（Execution Interface 为未来阶段）。

## 2. Runtime Action 设计

- **`platform/runtime-action/action-policy.yaml`**：Action 治理"宪法"。
  - **验收不变量**：ap-1 可执行动作必须先有 Proposal 且批准后才能进 Execution；ap-2 高风险必须显式人工批准、低风险可 auto-approve（记录在案）；ap-3 不得含 forbidden auto 字段；ap-4 Scheduler 只产出计划不产出自批准动作。
  - **action_types（6）**：run-command / trigger-workflow / write-file / deploy-artifact / release-publish / config-change。
  - **risk_levels（low/medium/high）**：medium→agent-approval（PM）、high→human-approval（human）、low→auto-approve。
  - **approval_states**：draft / pending / approved / rejected / cancelled。
  - **execution_interface**：`not-implemented` + gate `approved-action-only`；**not_implemented** 边界含 auto-approval / auto-bypass / auto-action-mutation。
- **`action-proposal-schema.yaml`**：Action Proposal / Ledger 字段白名单 + `forbidden_fields`（auto_exec / auto_approve / auto_bypass / executed / result 出现即 Action Contract 违规 Critical）。
- **`action-ledger-schema.yaml`**：集成台账字段集（root + proposal_ref + contract_ok）。
- **`snapshot-schema.yaml`**：快照只读留底字段集。
- **`action-template.yaml`**：新版 Action Proposal 模板（engops-lead / PM 人工创建）。

## 3. Action Proposal & Ledger & Snapshot

- **Proposal（`platform/runtime-action/records/`）**：每个 Action 一条提案。
  - `AP-0001-refund-calc-edit.yaml`（write-file / medium / **approved**，PM 批准）
  - `AP-0002-run-regression.yaml`（run-command / high / **pending**，等待人工批准）
  - `AP-0003-deploy-staging.yaml`（deploy-artifact / high / **draft**，仅创建未提交）
  - 全部**不含任何执行/结果字段**（只记录"已批准/待批准"，执行由未来 Execution Interface 处理）。
- **Ledger（`.ai/context/runtime-action/action-ledger.yaml`）**：`action_context_id=ac-refund-feature-001`、`task_id=refund-feature`（与 runtime-context 对齐）、`policy_version=1`、3 条 proposal_ref 全部 `contract_ok=true`、含 snapshot_refs。
- **快照（`.ai/context/runtime-action/snapshots/AS-20260921-0001.yaml`）**：`ledger.version` 变化时留底；含 proposals_summary 只读汇总；**快照只读、不用于自动执行**。

## 5. 硬性边界（强制）

- Action Policy / Proposal / Ledger / 快照**只记录、只提案、只检查**；无任何自动执行 / 调度 / 切换 / 选择 / 批准。
- 本层**不实现 Execution Interface**；任何 `auto-approval / auto-bypass / auto-action-mutation` 均为未实现边界。
- Action Proposal 与 Ledger **不得包含任何执行/结果字段**（auto_exec / auto_approve / auto_bypass / executed / result 出现即 Action Contract 违规 Critical）。
- 批准权归属明确：medium=PM、high=human；计划产出后必须经批准才允许（未来）进入执行。
